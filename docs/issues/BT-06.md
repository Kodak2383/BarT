# BT-06 — Tracer bullet: real icons, in the list that exists

**Mode:** 👤 HITL — *screen recording permission needs your click*
**needs:** BT-03, BT-15 · **blocks:** BT-07

## Why
Icon capture is the riskiest unknown in the whole plan: a new permission, an API we have not used
here, unknown cost per item. Building the whole new view on top of an unproven capture path would
mean finding out late. So: thinnest possible slice through every layer, displayed in the list that
is already there.

(After BT-15 this is also the app's only remaining reason to identify items at all — the view is
read-only, so an icon the user recognises replaces the name the accessibility API used to give.)

## Slice
ScreenCaptureKit → per-item cache → existing list row. The grid comes later (BT-07); this proves
the data flows.

## Visible result
The current item list shows each item's real icon to the left of its name.

## Done when
- Icons are captured via ScreenCaptureKit and cached per `storageKey`, fetched once per item, not
  per poll (PRD §3.2).
- The permission is requested the first time the Items view opens, with one sentence of context —
  not during the welcome window (R2-Q5).
- Without the permission the list keeps working and shows names only.
- Cost is measured and written into this issue: time for a full capture pass, and CPU while the
  window sits open.

## Files
new `BarT/Engine/ItemIconSource.swift`, `BarT/UI/SettingsView.swift`, possibly `BarT/Model/MenuBarItem*.swift`

## Acceptance needs you to
Grant screen recording once, then confirm the icons are the right ones.

## Cost, measured 2026-09-17

Twenty-seven windows in the bar, on an 8K display at 2x:

- **A full pass: 1.25 s**, and almost all of it is the one `SCShareableContent` round trip —
  skipping the two 10,000 pt separators took nothing off it. The per-window capture after that is
  cheap, which is why the pass fetches the whole list at once instead of asking per item.
- **CPU while the settings window sits open: 0.0 %** (three `ps` samples, two seconds apart),
  110 MB resident with every icon cached. A pass runs only when the window is open and the list
  actually changed — the two-second poll never triggers one, because the cache answers.
- **23 of 27 windows gave up an icon.** The four that did not are BarT's own separators and items
  whose window had gone by the time the pass reached it; they are remembered as failed so the
  pass does not retry them forever.

Two things were tried and rejected on the way:

- **Template images** (one line, legible in any appearance) throw the colour away: both
  temperature items turned into solid black pills. The icons now sit on a chip filled with the
  menu bar's own sampled colour instead — same legibility, real pixels.
- **Sampling the menu bar once per pass** is needed at all because the bar is translucent: with a
  dark desktop picture under a light system appearance, macOS draws every glyph white, and white
  glyphs are invisible on the settings window's background.

## Done 2026-09-17

Accepted live: with the permission granted on the new build, every row in the items list carries
its own icon — the twelve that all read "Control Center" are now a butterfly, two temperature
readings, a display, Bluetooth, CPU, RAM and disk meters. The riskiest unknown of the plan is
answered: ScreenCaptureKit hands out a status item's window on its own, hidden items included, and
it costs a second once per open window.

What BT-07 inherits: `ItemIconSource.icon(for:)` keyed by window ID, `menuBarTint` for the chip the
icons have to sit on, and `reset()` for when the permission changes. Nothing else needs to know
where the pixels came from.
